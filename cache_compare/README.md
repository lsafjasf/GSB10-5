# 缓存淘汰策略效果对比（库 + 自测）

纯 Python 3 标准库实现，无第三方依赖。用**带参数的合成访问模型**模拟四类典型负载，
在多个容量下从**命中率、缺失代价、元数据内存开销**三个维度对比 LRU / LFU / FIFO / Random，
并给出 100 万次访问的耗时与内存峰值。

## 文件

| 文件 | 内容 |
|---|---|
| `cache_policies.py` | 四种淘汰策略，统一 `access(key)` 接口，均为 O(1) |
| `workloads.py` | 四类带参数访问模型 + 真实轨迹文件加载接口 |
| `simulate.py` | 对照实验 + 100 万次基准，输出 Markdown 表格 |
| `test_cache.py` | `unittest` 边界用例与策略语义自测（11 个） |
| `results_raw.md` | 本机实际跑出的原始结果 |

## 策略说明与适用场景

| 策略 | 元数据 | 适用场景 | 不适用 / 风险 |
|---|---|---|---|
| **LRU** 最近最少使用 | 双向链表节点，约 **56 B/条** | 时间局部性强、访问热度随时间漂移的通用场景（文件系统页缓存、CPU cache、通用 KV）；无历史包袱 | 顺序扫描会把链表尾部的热点全部冲走（**扫描污染**）；链表指针开销大 |
| **LFU** 最不经常使用 | 频次计数 + 频次桶，约 **170–490 B/条** | 热度稳定的热点集中负载，且夹杂扫描/批处理；抗扫描污染 | 历史高频但已变冷的键长期占位（**频次老化**问题）；元数据最重、实现最慢 |
| **FIFO** 先进先出 | 队列指针，约 **8–18 B/条** | 容量小、追求极简与可预测延迟、访问近乎均匀的场景；适合嵌入式/低端设备 | 不利用任何访问信息，热点稍偏斜就明显落后 |
| **Random** 随机淘汰 | 一个指针槽，约 **9 B/条** | 超大规模、弱局部性、希望 O(1) 低开销且避免最坏情况（如部分内存数据库、CDN） | 偏斜负载下与 FIFO 相当，抓不住热点；结果随种子波动 |

> LFU 在容量越小、频次桶越分散时每条元数据越高（491 B/条 @ 100 条），
> 容量增大后频次桶复用、摊薄到约 170 B/条。LRU 恒定约 56 B/条。
> FIFO/Random 最省（deque 块和列表槽被条目摊薄到约 8–9 B/条）。

## 访问序列来源（合成模型，参数全部显式）

工作集 `N = 50,000` 键；固定种子 `20261005`，所有策略面对**完全相同**的序列；
缺失代价模型为 `1 + key % 10` ms（模拟异构回源延迟）。

| 负载 | 模型与参数 | 代表的真实负载 |
|---|---|---|
| `scan` | 循环顺序扫描 0..N-1 | 全表扫描 / 批处理 / 日志回放 |
| `uniform` | 均匀独立随机 | 哈希打散、无局部性的随机 ID 查询 |
| `zipf` | Zipf(skew=1.2)，CDF+二分采样 | Web/CDN/KV 的热点集中访问（流行度近似 Zipf，如 Wikipedia 轨迹） |
| `mixed` | 80% Zipf（前 10% 键为热点）+ 20% 顺序扫描 | 热点读为主、周期性夹杂备份/扫描的真实生产负载 |

`workloads.load_trace(path)` 支持每行一个 key（CSV 取首列）的真实轨迹文件，
可直接接入 Wikipedia CDN、S3-FIFO 论文等公开轨迹：

```bash
python3 simulate.py compare --trace wikipedia_2019us.csv --capacity 1000
```

## 100 万次访问：耗时与内存峰值

负载 `mixed`，容量 1,000，工作集 50,000；耗时用 `time.perf_counter`，
内存峰值用 `tracemalloc`（计时与测内存分两轮，互不干扰）。
机器：Python 3.12.3 / WSL2 x86_64 / AMD Ryzen 7 9700X。

| 策略 | 命中率 | 耗时(s) | 吞吐(M ops/s) | 内存峰值(MiB) |
|---|---:|---:|---:|---:|
| LRU | 67.20% | 0.32 | 3.11 | 0.37 |
| LFU | 73.12% | 0.44 | 2.27 | **0.61**（最高） |
| FIFO | 63.89% | **0.24** | **4.08** | **0.31**（最低） |
| Random | 63.89% | 0.31 | 3.28 | **0.31**（最低） |

## 结论与适用边界（跨容量一致成立）

1. **没有全场景最优策略，命中率不是唯一指标**：LFU 在 zipf/mixed 三个容量下命中率与缺失代价均第一
   （mixed 下命中率领先 LRU 1.4–9.2 个百分点，缺失代价低 6%–18%），但元数据开销是 LRU 的 3–9 倍、
   100 万次访问耗时约为 FIFO 的 1.8 倍、内存峰值约为 FIFO 的 2 倍。（墙钟耗时受机器负载影响，
重复运行在 ±30% 内波动；命中率与内存峰值逐字节级稳定。）
2. **顺序扫描下所有策略都无效**：容量远小于工作集时命中率 ≈ 0，谁也不比谁强——
   此时正确做法不是换策略，而是避开缓存（直接流式处理）或使用更大容量 / 扫描过滤（如 LRU-2K 思想）。
3. **均匀访问下策略无差异**（三容量均 ≈ 容量/工作集），此时选**元数据最省、最快**的 FIFO/Random；
   容量 10,000 时 Random 甚至以 19.51% 微胜，但差异在随机波动范围内。
4. **容量是边界的决定因素**：容量越小，LFU 相对 LRU 的命中率优势越大
   （zipf 容量 100 时 +8.7pp，容量 10,000 时仅 +0.08pp）——
   **缓存越紧张，越值得为 LFU 的高元数据/低速度买单；容量充裕时 LRU 的性价比更高**。
5. **热点稳定 + 有扫描 → LFU**；**热度随时间漂移 → LRU**（LFU 有频次老化问题，
   冷掉的老热点会赖着不走，生产中常改用带老化的 W-TinyLFU / S3-FIFO 等）；
   **弱局部性 / 极端省内存 → Random/FIFO**。
6. **缺失代价与命中率排序一致**：本实验回源代价与键弱相关，故两项指标同向；
   若回源代价强依赖键（热点恰是大对象），应直接优化"总缺失代价"而非命中率。

## 边界用例（`test_cache.py`，全部通过）

- 容量 0：永不缓存，重复访问也不命中；负容量按 0 处理
- 容量 1：同键重复命中，换键即淘汰
- 任意策略插入 100 个键到容量 3，缓存大小恒 ≤ 3
- LRU：命中后重新计序（1,2,1,3 → 淘汰 2）
- FIFO：命中不改序（1,2,1,3 → 淘汰 1）
- LFU：淘汰频次最低者（1 访问 2 次、2 访问 1 次 → 插入 3 时淘汰 2）
- 抗扫描：热点预热后插入 50 个冷键，LFU 保住全部热点（10/10），LRU 显著丢失
- Random：字典与候选数组始终一致，容量不越界
- 元数据 `bookkeeping_bytes()` 非负且随容量单调增长

## 运行命令

```bash
cd cache_compare

python3 -m unittest test_cache -v          # 自测（11 个用例）
python3 simulate.py compare                # 命中率/缺失代价/元数据对照（多容量）
python3 simulate.py bench                  # 100 万次访问耗时 + 内存峰值
python3 simulate.py all                    # 默认：两者都跑
python3 simulate.py compare --accesses 1000000          # 自定义访问次数
python3 simulate.py compare --trace real_trace.csv --capacity 1000  # 真实轨迹
```
