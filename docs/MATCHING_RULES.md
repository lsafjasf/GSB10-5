# 匹配规则说明

本文档定义 termcheck 的匹配与判定规则，并给出每条规则的依据。

## 1. 规范化（术语与文档使用完全相同的规则）

| 规则 | 实现 | 依据 |
| --- | --- | --- |
| 全半角折叠 | Unicode NFKC 逐字符规范化（`ＡＰＩ`→`API`、`１２３`→`123`、兼容字符折叠） | 全半角差异是排版差异而非术语差异；NFKC 是 Unicode 标准中处理此类兼容等价的标准方式 |
| 大小写折叠 | 规范化后做 `casefold()`，拉丁字母大小写不敏感（`Github` 能命中 `GitHub`） | 句首大写、标题大写等是排版要求，不应造成漏检；casefold 是 Unicode 推荐的无大小写比较方式 |
| 逐字符映射 | 规范化逐字符进行，并记录“规范化字符 → 原文偏移”的映射 | 保证命中位置可以精确映射回原文，冲突清单可复核 |

注意：规范化只用于“能否命中”。命中后会把原文片段与规范译名逐字比较，
仅大小写/全半角不同的规范译名用法（如 `Github`、`ＧｉｔＨｕｂ`）会被报告为
“大小写/全半角与规范译名不一致”，因为译名规范通常要求固定写法。

## 2. 词边界

- 拉丁术语（ASCII 字母/数字构成）：命中串两侧若仍是字母、数字或下划线，则不算命中。
  依据：防止 `cat` 命中 `concatenate`、`API` 命中 `APIKEY` 这类子串误报。
- CJK 术语（中日韩文字）：不要求词边界。
  依据：中文等语言没有空格分词，术语天然嵌入连续文本中。

## 3. 词形变化

- 仅对纯拉丁术语自动生成常见变形：复数（`s/es/ies`）、`-ing`、`-ed`（含去 e、双写尾字母）。
  多词术语只变化最后一个词。
- 采用“生成变形后精确匹配”，不做词干还原（stemming）。
  依据：词干还原会引入不确定的过度匹配（如 `apple`/`application` 类的误并），
  而术语检查要求结果可复核、规则确定；生成式变形覆盖了技术文档中绝大多数词形差异。
- CJK 术语不做词形处理（中文无词形变化）。

## 4. 冲突判定

术语库每条目 = 规范译名 + 已知变体译名（+ 可选上下文关键词）。

1. 命中**规范译名**（含其词形变化）→ 规范用法，不报告；
   仅大小写/全半角不同时按第 1 节报告。
2. 命中**变体译名** → 原则上判定为冲突（error）。
3. **一词多义消歧**：条目登记了上下文关键词时，
   只有在“同一句子内且距离不超过 60 字”的窗口内命中任一关键词才判定为冲突；
   否则降级为 review（待人工确认），并进入人工确认条目列表。
   依据：多义词的义项由所在句子决定（如“苹果”在“发布会/股价”句中是公司，
   在“吃/水果”句中是水果）；跨句关键词不构成消歧证据，故限定句内窗口。
4. **跨条目歧义**：某条目的变体恰是另一条目的规范译名时，无法自动判断应属哪个概念，
   一律降级为 review（待人工确认）。
5. **未登记的说法不报告**：不在术语库变体列表中的同义词、近义表达一律不报。
   依据：术语一致性约束的是“已审定译名”，把普通词汇的自由度留给译者，
   这是控制误报的核心原则。

## 5. 重叠命中

同一原文片段被多个模式命中时：

- 严格更长的命中优先（如规范译名“苹果公司”命中时，其中的变体“苹果”不再单报）；
- 跨度完全相同的多个命中全部保留，交给第 4.4 节的歧义判定。

## 6. 匹配引擎

多模式精确匹配使用 Aho-Corasick 自动机（数组存储，纯标准库实现），
扫描耗时与文本长度成线性关系、与术语条数无关，因此 10 万条术语下仍可用
（实测数据见 `reports/benchmark.md`）。
