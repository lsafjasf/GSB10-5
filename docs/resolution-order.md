# 依赖注入解析顺序说明

仅使用 Python 标准库。核心实现在 `di/container.py`，轨迹在 `di/trace.py`。

## 1. 解析顺序如何确定

组件声明两类边：

- **即时依赖**（`deps=("b", "c")` 里的字符串）：构造本组件前必须已构造，按声明顺序依次解析。
- **延迟依赖**（`deps=(lazy("b"),)`）：构造期只注入句柄，不参与排序（见第 4 节）。

一次 `resolve(root)` 分为两个阶段：

**阶段 0：静态环检测（构造任何实例之前）**

1. 从 `root` 沿即时边 BFS，求出根可达子图（未注册的依赖在此报 `MissingDependencyError`）。
2. 在该子图上跑迭代版 Tarjan 强连通分量（SCC）。
3. 大小 > 1 的 SCC，以及指向自身的单点 SCC，都是环；立即抛出 `CircularDependencyError`，
   此时没有任何工厂被执行（fail-fast）。

**阶段 1：迭代 DFS 后序构造（即时依赖图无环时）**

1. 从根入栈；帧记录「组件名 / 依赖列表 / 下一个依赖下标 / 已就绪的依赖实例」。
2. 帧按声明顺序取下一个依赖：
   - 依赖 `DONE`：直接复用单例（轨迹记 `CACHED`）；
   - 依赖 `PENDING`：记 `DEP-WAIT`，把该依赖压栈，先构造它；
   - 依赖 `BUILDING`：无环图下不可能出现；若由延迟取值触发则报动态环（第 4 节）。
3. 全部即时依赖就绪后：为本组件的每个延迟依赖创建 `LazyRef` 句柄（`LAZY-INJECT`，不取值），
   然后执行工厂（`BEGIN` → `END`），实例存入容器、状态置 `DONE`，并把实例回填父帧。
4. 栈空即根构造完成。

因此构造顺序是 DFS 的**后序**：每个组件严格晚于其全部即时依赖；
依赖之间的先后等于声明顺序；同名组件只构造一次（单例语义）。
无环图下该顺序是确定性、可复现的（`TestDeterminism` 验证两次轨迹完全一致）。
DFS 与 Tarjan 均为**迭代实现**，1 万个组件的线性链不会触发递归深度限制。

## 2. 解析轨迹

每个事件含：序号、相对本次操作起点的毫秒时间戳、构造栈深度、类型、说明。

| 事件 | 含义 |
| --- | --- |
| `RESOLVE-BEGIN/END` | 一次 `resolve` 的起止 |
| `VISIT` | 组件进入 `BUILDING` 状态 |
| `DEP-WAIT` | 声明等待某个即时依赖先构造 |
| `CACHED` | 依赖已构造，直接复用同一实例 |
| `LAZY-INJECT` | 注入延迟句柄，此时**不取值** |
| `BEGIN/END` | 工厂开始 / 完成 |
| `LAZY-ACCESS` | 延迟句柄第一次被真正取值 |
| `FAIL` | 工厂抛错，或延迟取值形成动态环 |
| `DISPOSE` | 回收一个本次新建的实例 |
| `CYCLE` | 静态环检测命中（随后抛出） |

完整样例轨迹见 `docs/demo-output.txt`（`python3 demo.py` 重新生成）。
渲染时视觉缩进上限 12 层，更深的链以 `[d=N]` 数字标注，避免深链文本 O(n²) 膨胀。

## 3. 环报告

`CircularDependencyError.report` 包含：

- 环的总数；
- 每个环的**全部成员**（即该 SCC 的完整成员，按名排序）；
- 每个环的一条具体路径（首尾相同；自环显示 `s -> s`）。

示例（两个不相交环 + 一个自环，外加不在环上的 `root`、`f` 不列入）：

```
共 3 个环，涉及 6 个组件: a, b, c, d, e, s
  环 #1: 成员[a, b, c]  路径: a -> b -> c -> a
  环 #2: 成员[d, e]  路径: d -> e -> d
  环 #3: 成员[s]  路径: s -> s
```

## 4. 延迟注入语义与取值时机

- 工厂签名中延迟依赖位置收到的是 `LazyRef` 句柄，不是实例；
- **何时真正取值**：只在句柄第一次被 `.get()`（或通过它访问属性）时，
  才触发目标组件及其即时依赖子树的构造，走与第 1 节相同的 DFS；
- 取值结果缓存在句柄上：第二次 `.get()` 不再构造，轨迹中 `LAZY-ACCESS` 只出现一次；
- 延迟边**不参与**静态拓扑/SCC 检测，因此可以用来解开「构造后才互相引用」的环。
  典型模式：`a` 延迟持有 `b`，`b` 即时持有 `a`；`a` 先构造，
  之后再取 `b`，`b` 工厂拿到的 `a` 是同一个已构造实例；
- **边界**：如果句柄在「某组件的工厂执行期间」被取值，而目标此刻处于 `BUILDING`，
  说明取值时机仍然形成了运行时环，抛 `LazyCycleError` 并给出动态环路径
  （如 `a -> b -> a`）。轨迹上表现为 `LAZY-ACCESS` 后紧跟 `FAIL`。

## 5. 构造失败后的回收

- 记录每次解析开始前已构造的位置 `built_before`；本次新建实例单独回收。
- 工厂失败时异常包装为 `ConstructionError`（原始异常在 `.original`）。
- 回收顺序 = 构造顺序的**严格逆序**（资源获取即初始化的逆操作）；
  对每个实例：调用其 `disposer`（如有）→ 移出容器 → 状态复位为 `PENDING`。
- 上一次成功解析遗留的单例**不回收**；回收后容器仍可继续使用。
- 某个 `disposer` 自身抛错只记录到轨迹，不中断后续回收（见 demo 场景 5b）。
- 延迟取值嵌套失败时，构建栈上残留的 `BUILDING` 节点同样统一复位。

## 6. 耗时与内存（1 万个组件）

环境：Python 3.12.3 / Linux x86_64 (WSL2)。每场景跑 3 次取中位数。

| 场景 | 纯解析耗时 (ms) | tracemalloc 监控下耗时 (ms) | 堆内存峰值 (MiB) |
| --- | ---: | ---: | ---: |
| 线性链（深 10000） | ~46 | ~228 | ~12.2 |
| 星型（root + 9999 叶子） | ~50 | ~235 | ~11.8 |
| 二叉树（10000 节点） | ~47 | ~204 | ~11.4 |

口径说明：纯耗时用 `perf_counter` 计 resolve 本身；内存峰值用 `tracemalloc`
度量 resolve 期间 Python 堆增量（监控器本身有 4–5 倍计时开销，故同时给出纯耗时）。
组件为极简工厂；事件轨迹本身也是内存占用的一部分（约 4 万事件/万组件）。
复现：`python3 benchmark.py [组件数]`。

## 7. 运行命令

```bash
# 自测（19 个用例：无依赖 / 线性链 / 菱形 / 多环 / 自环 / 延迟解环 /
# 延迟动态环 / 失败逆序回收 / disposer 抛错 / 未注册依赖 / 确定性）
python3 -m unittest discover -s tests -v

# 演示：顺序说明里提到的轨迹、环报告、取值时机、清理结果
python3 demo.py

# 1 万组件基准（耗时 + 内存峰值）
python3 benchmark.py
python3 benchmark.py 100000   # 可指定规模
```
