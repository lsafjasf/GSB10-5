# 回滚可行性验证 —— 验证面说明

## 为什么回滚不只是"把旧版本部署回去"

新版本运行期间会持续写入数据。旧版本二进制虽然还在，但它读取的是**新版本写下的字节**。
只要写入格式有任何一项超出旧版本的理解范围，回滚后旧版本就会启动失败、读到脏数据或静默丢数据。
因此回滚前必须对"新版本产物 → 旧版本读者"做逐条兼容性验证。

## 验证的四个兼容面及依据

### 1. 数据格式（data_format）
- **验证内容**：文件头（编码方式、格式版本号）、逐条记录的必填字段是否齐全、字段类型是否匹配、旧版本是否容忍未知字段。
- **依据**：旧版本的反序列化器是按旧 schema 生成的代码。必填字段缺失会在启动加载或首次读取时抛异常；类型不匹配会得到错误值；而大多数 JSON/Protobuf 风格的反序列化器对**未知字段是忽略**的——这是"仅新增字段可回滚"的理论基础，本库用 `OldVersionReader` 显式模拟了这一行为（未知键忽略、必填缺失报错、类型严格校验）。

### 2. 枚举取值（enum）
- **验证内容**：新版本中枚举字段实际写出的每一个取值，是否都在旧版本的封闭枚举集合内。
- **依据**：枚举是封闭集合，旧版本校验逻辑遇到集合外取值会拒绝该条记录（或写入时崩溃）。新增枚举值是真实事故中最高频的回滚阻断项之一，且**只影响部分记录**（本场景 10%），必须逐条扫描全量数据才能发现，不能靠抽样。

### 3. 索引结构（index）
- **验证内容**：索引文件的格式版本号是否在旧版本支持列表内；索引键的字段构成与顺序是否与旧版本定义一致；索引能否由存量数据重建。
- **依据**：索引是派生数据，但旧版本启动时会校验索引文件头。格式版本不支持或键布局变化时旧版本会拒绝加载；只要索引可由数据重建（rebuildable），删除后重建即可，属于"需先转换"；若索引包含新版本独有的计算结果且无法重建，则升级为"不可回滚"。

### 4. 接口契约（contract）
- **验证内容**：旧版本对外暴露的每个操作，在新版本中是否仍存在；旧契约中每个请求/响应字段是否仍存在且类型一致。
- **依据**：回滚后旧版本要重新对外服务，它依赖的下游数据/调用契约若已被新版本破坏（删除操作、删字段、改类型），回滚后接口会直接报错。新增字段/新增操作不影响旧版本，不在阻断项内。

## 结论分级与处理步骤

| 结论 | 判定条件 | 处理步骤 |
|---|---|---|
| 可回滚 ROLLBACK_OK | 四个兼容面全部通过（未知字段忽略不算阻断） | 直接回滚，无需数据转换 |
| 需先转换 NEEDS_CONVERSION | 存在不兼容项，但全部可转换（枚举可映射、索引可重建、字段可回填） | 1) 停写或进入维护窗口 2) 按清单逐项转换（枚举改写、删索引重建、字段回填） 3) 用本工具复跑验证全部通过 4) 执行回滚 |
| 不可回滚 NOT_ROLLBACKABLE | 存在不可转换项（必填字段被删导致数据永久缺失、契约操作被删、索引不可重建、枚举无映射） | 1) 禁止直接回滚 2) 从回滚前备份恢复受影响数据，或让新版本双写旧格式直至数据补齐 3) 复跑验证无阻断项后再回滚 |

## 场景覆盖

| 场景 | 新版本变更 | 预期结论 |
|---|---|---|
| fully_compatible | 无变更 | 可回滚 |
| additive_fields | 新增可选字段 email/remark | 可回滚（旧版本忽略未知字段） |
| new_enum_value | status 新增 PENDING_DELETE | 需先转换（映射回 SUSPENDED）；无映射时不可回滚 |
| index_change | idx_status 改复合键 + 索引格式 v2 | 需先转换（删除并重建索引） |
| destructive_change | 删除必填字段 name、删除 get_user 接口 | 不可回滚 |
